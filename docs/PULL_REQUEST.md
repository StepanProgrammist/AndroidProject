## Ветки

- `develop` — основная рабочая ветка, сюда вливаются изменения.
- `feature/*` — новый функционал, создаётся от `develop`.
- `fix/*` — исправление бага, создаётся от `develop`.

Прямые коммиты в `develop` запрещены — только через PR.

Правила оформления коммитов — в [`COMMIT.md`](COMMIT.md).

## Часть 1. Как делать пулл-реквест

### 1. Ветка

- Ветка создаётся от актуального `develop`.
- Название: `feature/<кратко>` или `fix/<кратко>`.
- Латиница, нижний регистр, слова через дефис.
- Примеры: `feature/auth-jwt`, `fix/empty-message`.

```bash
git checkout develop
git pull origin develop
git checkout -b feature/auth-jwt
```

### 2. Коммиты в ветке

Пока работаете в ветке — названия могут быть любыми: `wip`, `fixed typo`, `test`.

Но лучше сразу оформлять по формату:

```text
тип(тг#номер_задачи): что сделал
```

Типы:

| Тип | Когда использовать |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление бага |
| `docs` | документация |
| `refactor` | рефакторинг без изменения поведения |
| `test` | тесты |
| `chore` | служебные изменения |
| `style` | форматирование без изменения логики |
| `perf` | улучшение производительности |

Правила:
- Прошедшее время: «добавил», «исправил», «вынес».
- Все коммиты одной задачи — с одним номером `тг#номер`.
- После заголовка — пустая строка, затем описание (если нужно).
- Мелкие правки без задачи — без номера: `docs: опечатка в README`.

Подробнее — в [`COMMIT.md`](COMMIT.md).

### 3. Заголовок PR

- Строгого формата нет.
- Коротко описывает, что было сделано. Например: «Добавил команду /start».
- Не оставлять дефолтный заголовок вида `Merge pull request #12 from ...`.

### 4. Описание PR

Добавлять, если:
- изменение затрагивает несколько файлов или модулей;
- есть нюансы реализации;
- меняется поведение, API, конфиг или БД;
- нужны скриншоты/видео (UI);
- есть ограничения или что-то осталось за рамками задачи.

Можно не добавлять, если:
- опечатка, форматирование, мелкая правка документации.

Шаблон:

```markdown
## Что сделано
...

## Зачем
Задача: тг#2

## Как проверить
1. ...
2. ...

## Скриншоты
...

## Чек-лист
- [ ] Тесты проходят
- [ ] Линтер/форматтер без ошибок
- [ ] Нет секретов и отладочного кода
```

Шаблон лежит в [`.github/pull_request_template.md`](../.github/pull_request_template.md) и подставляется автоматически при создании PR, если файл есть в ветке по умолчанию.

### 5. Чек-лист перед созданием PR

- [ ] Ветка создана от актуального `develop`.
- [ ] Код собирается.
- [ ] Тесты проходят.
- [ ] Линтер/форматтер без ошибок.
- [ ] Нет лишних файлов (`.env`, `node_modules`, логи и т.п.).
- [ ] Нет конфликтов с `develop`.
- [ ] Заголовок и описание заполнены.
- [ ] Привязана задача `тг#номер`.

### 6. Создание PR

1. Открыть PR из `feature/...` или `fix/...` в `develop`.
2. Заполнить заголовок.
3. Заполнить описание (если нужно).
4. Привязать задачу.
5. Назначить ревьюера (лида).

### 7. Доработка после ревью

- Исправить замечания.
- Закоммитить и запушить в ту же ветку.
- Ответить на комментарии.
- Дождаться approve.

### 8. Слияние

- Только **Squash and merge**.
- Итоговое сообщение squash-коммита — по правилам [`COMMIT.md`](COMMIT.md).
- Ветку удалить после слияния.

## Часть 2. Как принимать пулл-реквест (лид)

### 1. Проверка до ревью

- [ ] PR из правильной ветки в `develop`.
- [ ] Заголовок коротко описывает изменения.
- [ ] Описание заполнено (если требуется).
- [ ] Привязана задача.
- [ ] Нет конфликтов с `develop`.
- [ ] CI/тесты зелёные.

### 2. Код-ревью

Проверить:
- логику и корректность;
- читаемость и стиль;
- соответствие задаче;
- отсутствие секретов, отладочного кода, закомментированных блоков;
- отсутствие лишних файлов;
- тесты на новое поведение.

Оставить замечания или approve.

### 3. Проверка заголовка и описания

- Заголовок коротко описывает, что сделано.
- Описание заполнено по шаблону, если требуется.
- Итоговое сообщение squash-коммита — по правилам [`COMMIT.md`](COMMIT.md).
- Не мержить с заголовком `Merge pull request #... from ...`.

### 4. Слияние

- Выбрать **Squash and merge**.
- Проверить итоговое сообщение коммита по [`COMMIT.md`](COMMIT.md).
- Удалить ветку.
- Убедиться, что `develop` остаётся зелёным.

### 5. Если PR не готов

- Вернуть на доработку.
- Указать конкретные замечания.
- Не мержить с «грязным» заголовком или пустым описанием, если оно требуется.
